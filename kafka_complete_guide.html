Part 1 — Foundations

1.1 What problem does Kafka solve?

Imagine a mid-sized e-commerce company. The Orders service needs to tell five other systems whenever an order is placed: Inventory (decrement stock), Billing (charge the card), Shipping (create a label), Recommendations (update the user's profile), and Analytics (log the event for dashboards).

The naive approach is for Orders to call each of those five services directly (point-to-point, usually REST/RPC). This quickly becomes a nightmare:

  • N×M problem: with 10 services all needing to talk to each other, you end up with up to 90 point-to-point connections, each with its own retry logic, timeout handling, and failure mode.
  • Tight coupling: Orders cannot ship until it gets a response from all five downstream systems — if Shipping is down, does the whole order fail?
  • No replay: if Analytics was down for an hour and missed events, that data is gone unless someone built a special backfill mechanism.
  • Scaling pain: adding a sixth consumer of "order placed" events means changing the Orders service's code.

This is sometimes drawn as a "spaghetti diagram" — every box connected to every other box.

text
   Orders ───────► Inventory
     │  │  │  ╲
     │  │  │   ╲──► Billing
     │  │  └──────► Shipping
     │  └─────────► Recommendations
     └────────────► Analytics

Kafka inverts this. Instead of services calling each other, every service publishes events to Kafka, and any number of other services subscribe to the events they care about — without the publisher knowing or caring who's listening.

text
                         ┌──────────────┐
   Orders ───events────► │              │ ───► Inventory
   Payments ──events────►│ Apache Kafka │ ───► Billing
   Shipping ──events────►│  (the bus)   │ ───► Shipping
                         │              │ ───► Recommendations
                         └──────────────┘ ───► Analytics

This pattern is called event-driven architecture, and Kafka is the most widely used backbone for it. Concretely, Kafka is a distributed event streaming platform that does three things extremely well:

  1. Publish and subscribe to streams of records (like a message queue).
  2. Store streams of records durably and reliably, for as long as you want (like a filesystem or database).
  3. Process streams of records as they occur (stream processing).

The key insight that makes Kafka different from a traditional message queue: Kafka stores everything it receives, on disk, in order, for a configurable retention period (which can be "forever"). A consumer can join a topic and read from the beginning, from the latest message, or from any point in between. This single property — durable, replayable, ordered storage — is what unlocks event-driven architecture, stream processing, and "replay the last 7 days of clicks" use cases that a normal message queue can't do well.

1.2 A short history

  • 2010–2011: Engineers at LinkedIn (Jay Kreps, Neha Narkhede, Jun Rao) needed a system to handle the explosion of "activity data" (page views, clicks) and operational metrics flowing between systems. Existing message queues weren't built for this throughput or for log-style replay. They built Kafka internally and open-sourced it in early 2011.
  • 2012: Kafka became an Apache Software Foundation top-level project.
  • 2014: The original creators left LinkedIn to found Confluent, a company built around commercializing and extending Kafka (Schema Registry, Kafka Connect ecosystem, ksqlDB, fully-managed cloud Kafka).
  • 2017 onward: Kafka added Kafka Connect (no-code integration), Kafka Streams (a stream-processing library), and exactly-once semantics (transactions).
  • 2021–2022 (KIP-500): Kafka removed its dependency on Apache ZooKeeper for metadata management, replacing it with a self-managed Raft-based quorum called KRaft. As of Kafka 3.x+, KRaft is production-ready and is the default/recommended mode for new clusters (ZooKeeper mode was removed in Kafka 4.0).
  • Today: Kafka (and Kafka-API-compatible systems like Confluent Cloud, Amazon MSK, Redpanda, WarpStream) is the de facto standard for event streaming, used by the majority of Fortune 500 companies — Netflix, Uber, LinkedIn, Airbnb, Goldman Sachs, Walmart, and thousands of others.

1.3 Kafka vs. traditional message queues vs. databases

It's worth being precise about what Kafka is not, because beginners often mis-map it onto tools they already know.

PropertyTraditional MQ (RabbitMQ, ActiveMQ, SQS)Apache KafkaRelational Database
Primary abstractionQueue (message removed once consumed)Append-only log (message retained per retention policy)Tables of mutable rows
Multiple consumers of the same messageUsually needs fan-out exchanges / multiple queuesNative — any number of consumer groups read independentlyN/A
Replay old dataGenerally noYes — re-read from any offsetYes, but it's "current state," not a stream
ThroughputModerate (thousands–tens of thousands msg/s typical)Very high (millions of msg/s per cluster)N/A
Message orderingPer-queue, sometimes per-message-groupStrict ordering within a partitionN/A
Use case fitTask queues, RPC-style messaging, work distributionEvent streaming, log aggregation, CDC, real-time analytics, decoupling microservicesStoring and querying current application state

A simple way to remember it: a queue is a to-do list (each item is done once); a Kafka topic is a diary (every entry stays, and anyone can read any page, any number of times).

Kafka is also frequently compared to (and used alongside) Apache Pulsar (similar pub/sub + streaming model, separates storage/serving), and newer Kafka-protocol-compatible engines like Redpanda and WarpStream (drop-in replacements optimized for different cost/operational tradeoffs). For this guide we focus on Apache Kafka itself, since the concepts transfer almost directly to these alternatives.

1.4 Where data engineers use Kafka in the real world

  • CDC (Change Data Capture): Stream every row-level change from a production Postgres/MySQL database into Kafka (via Debezium) so downstream systems (data warehouse, search index, cache) stay in sync without hammering the source database with polling queries.
  • Log and event aggregation: Centralize logs, clickstream events, and application metrics from thousands of services into Kafka, then fan them out to Elasticsearch, S3/data lake, and real-time dashboards.
  • Decoupling microservices: Replace fragile synchronous REST chains with asynchronous event publishing (the "Orders" example above).
  • Real-time analytics & ML features: Feed live feature pipelines (fraud scores, recommendation signals, surge pricing) that need sub-second freshness.
  • Stream-to-lake ingestion: Land high-volume topics into Apache Iceberg / Delta Lake / S3 / Snowflake as the durable, queryable system of record, often via Kafka Connect or Flink.
  • Event sourcing: Store every state-changing event for an entity (e.g., an order's full lifecycle) as the source of truth, rebuilding "current state" views by replaying the log.
  • Data mesh / domain-oriented data products: Each domain team owns and publishes its topics as a versioned, discoverable "data product" that other teams subscribe to — this is exactly the model Netflix's Data Mesh platform implements (see Part 11).

Part 2 — Core Concepts

2.1 The mental model: a distributed commit log

The single most important mental model in Kafka: a topic is a log file, split into partitions, replicated across machines. Everything else in Kafka is built on top of this idea.

text
Topic: "page_views"   (an append-only log, split into 3 partitions)

Partition 0:  [msg0][msg1][msg2][msg3][msg4][msg5]──► new messages appended here
Partition 1:  [msg0][msg1][msg2][msg3]──────────────► new messages appended here
Partition 2:  [msg0][msg1][msg2][msg3][msg4]─────────► new messages appended here

Each box is an immutable record. New records are only ever appended to the end of a partition — nothing is ever inserted in the middle or updated in place. Each record gets a sequential ID within its partition called an offset (0, 1, 2, 3...).

2.2 Topics & Partitions

A topic is a named stream of records — think of it as a table name or a category (orders, page_views, payment_events). A topic is split into one or more partitions, which are the actual unit of storage, parallelism, and ordering.

Why split into partitions at all?

  1. Parallelism: a topic with 12 partitions can be read by up to 12 consumers in parallel (one partition per consumer), and written to by many producers in parallel.
  2. Scalability: partitions can be spread across many brokers (machines), so a topic's total throughput isn't capped by a single machine's disk/network.
  3. Ordering boundary: Kafka only guarantees order within a partition, not across an entire topic. This is a deliberate tradeoff — global ordering across partitions would require a global bottleneck.
text
Topic: "orders" — 4 partitions, spread across a 3-broker cluster

   Broker 1                Broker 2                Broker 3
 ┌───────────┐          ┌───────────┐          ┌───────────┐
 │Partition 0│          │Partition 1│          │Partition 2│
 │ (leader)  │          │ (leader)  │          │ (leader)  │
 └───────────┘          └───────────┘          └───────────┘
 ┌───────────┐          ┌───────────┐
 │Partition 3│          │Partition 0│ (replica)
 │ (leader)  │          └───────────┘
 └───────────┘

A practical consequence: if you need all events about the same entity (e.g., the same customer, the same order ID) to be processed in order, they must land in the same partition. Kafka achieves this by default through key-based partitioning (see §2.3 and §5.4).

2.3 Producers

A producer is any client application that publishes (writes) records to a Kafka topic. A record is a key-value pair (the key is optional). The producer decides — directly or via a partitioning strategy — which partition each record goes to. Producers are "dumb" in the sense that they don't need to know who, if anyone, is consuming the topic.

2.4 Consumers & Consumer Groups

A consumer reads records from one or more partitions, tracking its position via offsets. The really powerful idea is the consumer group: a named group of consumer instances that cooperatively divide up the partitions of a topic so that each partition is read by exactly one consumer in the group — giving you parallelism without duplicate processing.

text
Topic "orders" — 4 partitions          Consumer Group "billing-service"
┌───────────┐                          ┌─────────────┐
│Partition 0│ ───────────────────────► │ Consumer A   │
└───────────┘                          └─────────────┘
┌───────────┐                          ┌─────────────┐
│Partition 1│ ───────────────────────► │ Consumer B   │
└───────────┘                          └─────────────┘
┌───────────┐                          ┌─────────────┐
│Partition 2│ ──────┐                  │ Consumer C   │
└───────────┘       ├────────────────► │ (reads P2 & P3)
┌───────────┐       │                  └─────────────┘
│Partition 3│ ──────┘
└───────────┘

Crucially, multiple consumer groups can read the same topic completely independently, each maintaining its own offsets. This is what gives Kafka its pub/sub fan-out power: the analytics group and the fraud-detection group can both read every event in orders, at their own pace, without affecting each other.

A consumer group can have at most as many active consumers as the topic has partitions — extra consumers beyond that sit idle. This is the single most common scaling mistake beginners make (see §10.6).

2.5 Brokers & Clusters

A broker is a single Kafka server — a process that stores partitions and serves produce/fetch requests. A cluster is a group of brokers working together. One broker in the cluster acts as the controller, responsible for cluster-wide metadata decisions like electing partition leaders (in KRaft mode, this is handled by a quorum of controller nodes rather than a single broker — see §2.8). Clients (producers/consumers) connect to any broker to discover the full cluster metadata (which broker leads which partition) and then talk directly to the relevant broker.

2.6 Offsets

An offset is a monotonically increasing integer that uniquely identifies a record's position within a partition. Offsets are partition-local — partition 0 and partition 1 of the same topic both have their own offset 0, offset 1, etc. A consumer's "position" in a partition is just an offset number, and committing an offset means telling Kafka "I've successfully processed up through this point," which is recorded in a special internal topic called __consumer_offsets.

This is the mechanism that allows a consumer to crash, restart, and resume exactly where it left off — and it's why Kafka is so good at replay: you can manually reset a consumer group's offset back to an earlier point (or to the very beginning) and it will reprocess everything from there.

2.7 Replication: Leaders, Followers, ISR

Every partition can be replicated across multiple brokers for fault tolerance, controlled by the topic's replication factor (commonly 3 in production). For each partition:

  • One replica is the leader — it handles all reads and writes for that partition.
  • The other replicas are followers — they continuously fetch (replicate) data from the leader to stay in sync, but serve no client traffic by default.
  • The set of replicas that are sufficiently caught-up with the leader is called the In-Sync Replica set (ISR). Only ISR members are eligible to become the new leader if the current leader fails.
text
Partition 0, replication factor = 3

Broker 1 (Leader)  ──┐  followers pull data from leader
  [data up to offset 105]
                       │
Broker 2 (Follower) ◄──┘  [synced up to offset 105] ── in ISR
Broker 3 (Follower) ◄─────[synced up to offset 102] ── lagging, may drop out of ISR

If Broker 1 dies, the controller picks a new leader from the ISR (here, Broker 2, since it's fully caught up) — this is a leader election, and it's how Kafka survives broker failures without losing committed data (as long as you've configured durability settings correctly — see §3.3).

2.8 ZooKeeper vs. KRaft

Historically, Kafka relied on Apache ZooKeeper as an external coordination service to store cluster metadata (which brokers exist, topic configs, partition leader info, ACLs) and to elect the controller. This worked but added an entire second distributed system to operate, patch, and scale, and it limited how many partitions a cluster could practically hold (ZooKeeper became a bottleneck at very large partition counts).

KRaft (Kafka Raft metadata mode), introduced via KIP-500, removes ZooKeeper entirely. Instead, a small set of Kafka brokers are designated as controllers, and they replicate metadata among themselves using the Raft consensus protocol — the same family of algorithm used by etcd, Consul, and CockroachDB. Benefits: one system to operate instead of two, faster controller failover, and support for many more partitions per cluster. As of Kafka 3.x, KRaft is production-recommended for new clusters, and Kafka 4.0 removed ZooKeeper support entirely. If you're starting fresh today, you should use KRaft.

2.9 Anatomy of a Kafka record

Every record (message) in Kafka has this structure:

text
┌─────────────────────────────────────────────────────────┐
│ Key        (optional, bytes)  — used for partitioning    │
│ Value      (bytes)             — the actual payload      │
│ Timestamp  (event time or log-append time)               │
│ Headers    (optional key-value metadata, like HTTP headers)│
│ Partition  (which partition it landed in)                │
│ Offset     (its position within that partition)          │
└─────────────────────────────────────────────────────────┘

Example, conceptually, for an order event:

text
Key:     "customer-8841"          (so all of this customer's orders land in one partition)
Value:   {"order_id": "o-991", "amount": 49.99, "currency": "USD"}
Headers: trace-id=abc123, schema-version=3
Timestamp: 2026-06-18T09:14:02Z

Part 3 — How Kafka Actually Works (Internals)

This section is what separates "I can use Kafka" from "I understand Kafka" — the knowledge you need to debug production incidents and make good design decisions.

3.1 The log: segments, indexes, and the filesystem

A partition isn't one giant file — it's split into segments, each a pair of files on disk:

text
/var/kafka-logs/orders-0/
   00000000000000000000.log     ← segment 1 (records, offsets 0-999999)
   00000000000000000000.index   ← offset index (sparse, for fast seeks)
   00000000000000000000.timeindex ← timestamp index
   00000000001000000000.log     ← segment 2 (records, offsets 1000000+)
   00000000001000000000.index
   ...

Only the active segment (the last one) is appended to. Older segments are closed and immutable. This design is what allows Kafka to:

  • Delete old data cheaply: dropping an entire old segment file is a simple file deletion, not a row-by-row scan.
  • Achieve very high write throughput: Kafka appends sequentially to the active segment and relies heavily on the OS page cache and sendfile() zero-copy transfer to serve reads, avoiding extra copies between kernel and application memory. This sequential-disk-I/O design is a major reason Kafka outperforms systems built on random-access storage for this workload.
  • Seek efficiently by offset or timestamp: the .index and .timeindex files are sparse lookup tables that map offsets/timestamps to approximate byte positions in the .log file, so a consumer asking "give me everything after offset 4,500,000" doesn't need to scan from the start.

3.2 Partitioning and ordering guarantees

Kafka's ordering guarantee is precise and important to internalize: records are guaranteed to be delivered to a consumer in the order they were written, but only within a single partition. There is no ordering guarantee across partitions.

This means the partitioning strategy is a design decision with real consequences:

  • If you need strict ordering for "all events for order #4471," you must ensure they all hash to the same partition — which happens automatically if you use the order ID as the record key (Kafka's default partitioner hashes the key to pick a partition deterministically).
  • If you don't care about ordering across different entities (e.g., independent sensor readings from different devices), you can use a null key and let Kafka round-robin across partitions for better load balancing.
  • More partitions = more parallelism, but also: more open file handles per broker, slower leader elections, and (since Kafka 3.x improvements help, but it's still a factor) more replication overhead. Don't over-partition "just in case" — see §10.1 for sizing guidance.

3.3 Replication protocol deep dive

This is one of the most commonly misunderstood — and most commonly misconfigured — parts of Kafka, and misconfiguration here is the difference between "Kafka never loses data" and "Kafka silently lost data during an outage."

Key configs that control durability:

ConfigWhere setWhat it does
replication.factorTopicHow many total copies of each partition exist (e.g., 3)
min.insync.replicasTopic/brokerMinimum number of replicas (including leader) that must acknowledge a write for it to be considered "committed" when acks=all
acksProducer0 = fire and forget; 1 = leader only; all/-1 = wait for all in-sync replicas
unclean.leader.election.enableBroker/topicWhether a non-ISR replica is allowed to become leader (risking data loss) if no ISR replica is available

The classic safe production configuration is replication.factor=3, min.insync.replicas=2, acks=all, unclean.leader.election.enable=false. With this setup, a write is only acknowledged once at least 2 of the 3 replicas have it, so you can lose any one broker without losing acknowledged data, and Kafka will refuse to elect a leader that would silently drop committed data.

What actually happens during a leader failure:

  1. Broker hosting the leader for partition 0 crashes.
  2. The controller (quorum, in KRaft) detects this via session timeout / heartbeat failure.
  3. The controller picks a new leader from the partition's current ISR list and propagates the new partition metadata to all brokers.
  4. Producers and consumers, which periodically refresh their metadata (and immediately on a NotLeaderForPartition error), redirect their requests to the new leader.
  5. The failed broker, once it rejoins, becomes a follower and catches up by replicating from the new leader.

This entire process typically takes a few seconds — which is why producers and consumers need sensible retry/timeout settings (covered in Parts 5 and 6) to ride out the brief unavailability window rather than throwing errors to the application.

3.4 Retention: delete vs. compact

Kafka topics have a cleanup policy, set per topic:

  • delete (default): records are removed once they exceed retention.ms (time-based, e.g., 7 days) or retention.bytes (size-based). This is what you want for event streams like clickstream or logs, where you only care about a recent window.
  • compact: Kafka guarantees to retain at least the last value for each key, removing older values for the same key in the background (a process called log compaction). This turns a topic into something closer to a changelog/snapshot of current state per key — exactly what's needed to back things like Kafka Streams' state stores, or to represent "current account balance per user ID" rather than "every balance change ever." You can also combine compact,delete to compact but still eventually drop very old keys.
text
Before compaction (key, value):           After compaction:
(user1, balance=10)                       (user1, balance=130)
(user2, balance=50)                       (user2, balance=50)
(user1, balance=80)
(user1, balance=130)   ← latest for user1

3.5 What happens when a producer sends a message

Understanding this flow explains almost every producer config you'll ever tune (Part 5):

  1. The application calls producer.send(record). This is asynchronous — it returns immediately with a Future, it does not block on the network by default.
  2. The record is serialized (key & value turned into bytes) and handed to a partitioner, which decides which partition it belongs to.
  3. The record is placed into an in-memory per-partition batch buffer (buffer.memory), not sent immediately.
  4. The producer's background I/O thread sends a batch once either: it's full (batch.size), or linger.ms milliseconds have elapsed since the batch started filling (whichever comes first). This batching is the main lever for throughput vs. latency tradeoffs.
  5. The batch (optionally compressed — compression.type) is sent to the partition's leader broker.
  6. The broker appends it to the partition's log, replicates to followers, and replies once the durability bar set by acks is met.
  7. The producer's Future completes (success → offset/partition metadata; failure → exception, possibly after internal retries).

3.6 What happens when a consumer polls

  1. The consumer calls poll(timeout) in a loop. This single call does a lot: it sends heartbeats to the group coordinator (keeping group membership alive), fetches new records from each assigned partition's leader (prefetched into an internal buffer for efficiency), and returns whatever records are ready.
  2. The application processes the returned records.
  3. The application (or the client library, if auto-commit is on) commits offsets, marking progress.
  4. Loop back to step 1.

The critical operational detail: if your processing logic between poll() calls takes too long (longer than max.poll.interval.ms), Kafka assumes the consumer is dead and kicks it out of the group, triggering a rebalance — even if the consumer's process is technically still alive and just slow. This is one of the most common production bugs (see §10.6).

3.7 Consumer group rebalancing protocols

A rebalance is the process of reassigning partitions among the members of a consumer group — triggered when a consumer joins, leaves, crashes, or a topic's partition count changes.

  • Eager rebalancing (legacy default): all consumers in the group give up all their partitions, then partitions are reassigned from scratch. Simple, but causes a "stop-the-world" pause for the entire group, even for consumers whose assignment doesn't change.
  • Cooperative sticky rebalancing (CooperativeStickyAssignor, the modern recommended default): only the specific partitions that need to move are reassigned; consumers keep processing the partitions they're keeping. This dramatically reduces rebalance-induced downtime, especially for groups with many consumers or large state (e.g., Kafka Streams apps with local state stores).
  • Static group membership (group.instance.id): tells Kafka "this is the same logical consumer instance restarting," letting it skip a rebalance entirely on quick restarts/deploys, rather than treating the restart as a leave + rejoin.

3.8 Exactly-once semantics: idempotence & transactions

By default, Kafka gives you at-least-once delivery: if a producer doesn't receive an acknowledgment (e.g., due to a network blip) it retries, which can result in the same message being written twice. Kafka layers two features on top to get exactly-once:

  • Idempotent producer (enable.idempotence=true, the default since Kafka 3.0 when not explicitly disabled): the producer is assigned a unique ID and tags each batch with a sequence number. The broker detects and silently drops duplicate retries, so retries become safe — you get exactly-once per partition, per producer session without any application code changes.
  • Transactions: allow a producer to write to multiple partitions/topics atomically — either all of the writes become visible to consumers, or none do. This is what powers Kafka Streams' and Connect's exactly-once processing guarantees: "read from input topic, process, write to output topic, commit input offset" all happen as one atomic unit, so a crash mid-processing can't result in double-processing or lost updates.

It's worth being precise: exactly-once is a guarantee about Kafka-to-Kafka pipelines (or Kafka + a transactional sink that participates in the two-phase protocol). If your consumer's side effect is "call a non-transactional external API" or "write to a database that isn't coordinated with Kafka's transaction," you're back to needing idempotent application logic (e.g., upserts keyed by a unique event ID) to achieve effectively-once outcomes end-to-end.

4.3 Designing a topic: partitions, replication, retention

A few practical rules of thumb when creating a topic:

  • Partitions: start with enough to support your target consumer parallelism (partitions ≥ max number of consumer instances you'll ever run in one group), but don't go overboard — more partitions means more replication traffic, more open files, and slower controller failover. A common starting point for a moderate-throughput topic is 6–12 partitions; very high-throughput topics at large companies may have 50-100+.
  • Replication factor: 3 is the standard production default (survives 1 broker failure with min.insync.replicas=2, or 2 broker failures with weaker durability).
  • Retention: set based on your replay/recovery needs, not just "how long until I run out of disk." A common pattern: keep 3-7 days in Kafka for replay/recovery, and land everything older into cheap long-term storage (S3, Iceberg) via Kafka Connect or a stream processor.
  • Key/partitioning choice: decide before you have production traffic, because changing the number of partitions later changes which keys land in which partition (breaking ordering guarantees for existing keys) — this is a one-way decision in practice.

5.4 Partitioning strategies

  • Default behavior: if a key is provided, Kafka hashes the key (murmur2) to deterministically pick a partition — same key always goes to the same partition (as long as partition count doesn't change). If no key is provided, the default "sticky" partitioner batches records onto one partition at a time before round-robining, to improve batching efficiency.
  • Custom partitioner: implement the Partitioner interface when you need domain-specific logic — e.g., routing VIP customers' events to a dedicated set of partitions for priority processing, or routing by geographic region.
  • The golden rule: pick your partitioning key based on what needs to stay in order relative to itself. For order events, that's the order ID or customer ID — not, say, a random UUID per event, which would destroy ordering guarantees and also tends to spread load evenly (sometimes desirable, sometimes not).

5.5 Serialization: String, JSON, Avro, Protobuf

Kafka itself only knows about bytes — serialization format is a client-side concern.

  • String/JSON: simplest to start with, human-readable, but no enforced schema (any producer bug can silently send malformed JSON that breaks every downstream consumer), and JSON is verbose (larger messages, more disk/network cost).
  • Avro: compact binary format, schema-driven, mature integration with Kafka's ecosystem (Confluent Schema Registry, Kafka Connect, ksqlDB). The schema travels separately (in the registry), not duplicated in every message — only a small schema ID is embedded. This is the most common production choice in the Kafka ecosystem and is what Netflix uses for its event topics (see Part 11).
  • Protobuf: similarly compact and schema-driven, more popular outside the Kafka-specific ecosystem (gRPC services), strong multi-language code generation. A reasonable choice if your organization is already Protobuf-heavy.
  • JSON Schema: a middle ground — keeps JSON's readability while adding schema enforcement and registry integration.

We cover schema management and evolution in depth in Part 7, because this is one of the highest-leverage decisions you'll make — a topic with no schema discipline becomes nearly impossible to evolve safely once a dozen teams depend on it.

6.3 Offset commits: auto vs manual

  • Auto-commit (enable.auto.commit=true, default): the client commits offsets periodically (auto.commit.interval.ms) in the background, regardless of whether your application actually finished processing those records. Simple, but dangerous: if your app crashes after the auto-commit but before finishing processing, you silently lose those records (effectively "at-most-once" in failure scenarios) — or if it commits before you push downstream, a crash mid-batch can also cause gaps.
  • Manual commit (enable.auto.commit=false): your application explicitly calls commitSync()/commitAsync() only after it has successfully finished processing a batch of records. This is the correct choice for any pipeline where data loss or duplication matters — i.e., almost all real production data pipelines.

6.4 Delivery semantics: at-most-once, at-least-once, exactly-once

SemanticHow you get itRisk
At-most-onceCommit offsets before processingIf processing fails after commit, the message is lost forever
At-least-onceCommit offsets after successful processing (the common default for most pipelines)If a crash happens after processing but before commit, the message is reprocessed — your downstream logic must be idempotent (e.g., upsert by ID, not blind insert)
Exactly-onceKafka transactions end-to-end (read-process-write all atomic), or idempotent downstream writes (e.g., upsert keyed by a dedup ID)More complex to set up; only available natively for Kafka→Kafka or Kafka→transactional-sink pipelines

In practice, the overwhelmingly common production pattern is at-least-once delivery + idempotent consumers (e.g., "upsert this row by primary key" rather than "always insert a new row") — this gets you the practical effect of exactly-once without the complexity of distributed transactions.

6.5 Handling failures: retries, DLQ, poison pills

A poison pill is a message that consistently fails processing no matter how many times you retry it (e.g., malformed data that throws a parsing exception every time). Without a strategy for this, a poison pill can block an entire partition forever, since Kafka requires the consumer to make progress in offset order.

The standard production pattern:

text
                  ┌─────────────┐  fails N times   ┌───────────────────┐
Topic: orders ───►│  Consumer   │ ───────────────► │ Topic: orders-dlq  │
                  │ (retry logic)│                   │ (dead letter queue)│
                  └─────────────┘                   └───────────────────┘
                         │ succeeds
                         ▼
                 downstream processing
  1. On a processing failure, retry a few times with backoff (in-process, or via a retry topic with increasing delay).
  2. If it still fails after N attempts, publish the original message (plus error context: exception message, stack trace, timestamp) to a dead-letter topic (e.g., orders-dlq) and commit the offset on the main topic so the partition keeps moving.
  3. Alert on DLQ volume, and have a separate process (automated or manual) to inspect and potentially replay DLQ messages once the root cause is fixed.

Kafka Connect has this pattern built in (errors.tolerance=all + errors.deadletterqueue.topic.name), and it's straightforward to implement yourself in a Kafka Streams or plain consumer application.

Part 7 — Schema Management

7.1 Why schemas matter in streaming

In a request/response API, a schema mismatch fails loudly and immediately — the caller gets an error right away. In streaming, a producer might write malformed or incompatible data, and the failure won't surface until some consumer — possibly owned by a completely different team, possibly days later — tries to read it and crashes. Because Kafka decouples producers from consumers (that's the whole point!), schema discipline is what keeps that decoupling from turning into chaos.

7.2 Schema Registry

A Schema Registry (Confluent Schema Registry is the most widely used; AWS Glue Schema Registry and others exist too) is a separate service that stores versioned schemas for your topics and enforces compatibility rules when a new schema version is registered.

text
Producer                  Schema Registry              Kafka Broker
   │  1. "what's the         │
   │     current schema ID    │
   │     for this topic?"     │

   │ ◄─────────────────────── │
   │  2. schema ID = 7        │
   │                                                     │
   │  3. serialize record as: [schema_id=7][avro bytes] │

7.4 Schema evolution & compatibility modes

Schemas change over time (a new field, a renamed field, a removed field). The Schema Registry enforces a compatibility mode per subject (topic) to prevent a producer from breaking existing consumers:

  • BACKWARD: a new schema can read data written by the previous schema. This is the most common default — it lets consumers upgrade before producers (new consumer code can still read old messages).
  • FORWARD: data written with the new schema can be read by consumers still using the previous schema — this lets producers upgrade before consumers.
  • FULL: both backward and forward compatible.
  • NONE: no checks (not recommended for shared production topics).

Safe evolution moves (under BACKWARD compatibility) include adding a new field with a default value, and removing a field that had a default. Unsafe moves include renaming a field (looks like "remove + add" to the registry) or changing a field's type incompatibly — these will be rejected by the registry before they ever reach production, which is exactly the point.

Part 9 — Stream Processing

9.1 Kafka Streams

Kafka Streams is a Java library (bundled inside Kafka itself — no separate cluster to run) that lets you write stateful, fault-tolerant stream processing applications against Kafka topics. Because it's just a library, you deploy it as part of your normal application JAR — no YARN, no Flink cluster, no extra infrastructure. The application itself is the stream processing cluster, and multiple instances of the same app automatically partition the work among themselves (using the same consumer group mechanism).

java
// Word-count style example — counting order events per customer in a sliding window
StreamsBuilder builder = new StreamsBuilder();

KStream<String, String> orders = builder.stream("orders");  // key = customerId

KTable<Windowed<String>, Long> orderCounts = orders
    .groupByKey()
    .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(5)))
    .count();

orderCounts.toStream()
    .map((windowedKey, count) ->
        KeyValue.pair(windowedKey.key(),
                      String.format("{\"customer\":\"%s\",\"orders_last_5min\":%d}",
                                    windowedKey.key(), count)))
    .to("order-counts-by-customer");  // write results back to Kafka

KafkaStreams streams = new KafkaStreams(builder.build(), props);
streams.start();

Key Kafka Streams concepts:

  • KStream: an infinite, unbounded stream of records (like a SELECT from a table that never ends).
  • KTable: a stream interpreted as a changelog — each record with the same key overwrites the previous one. Represents the "latest state" per key (like a database table).
  • GlobalKTable: a KTable that's fully replicated to every instance of your app — used for broadcasting reference data (lookup tables) for enrichment without shuffling.
  • State stores: local RocksDB databases that Kafka Streams manages per-partition, backed up to Kafka changelog topics for fault tolerance. This is how windowed aggregations, joins, and custom stateful operations persist their state.
  • Processing topology: the DAG of operations you define with the Streams DSL or Processor API — Kafka Streams compiles this into efficient internal task graphs.

9.2 ksqlDB

ksqlDB gives you a SQL interface on top of Kafka Streams, letting you write streaming pipelines in SQL rather than Java code. This dramatically lowers the bar for teams that know SQL but not Java:

sql
-- Create a stream on top of the orders topic
CREATE STREAM orders_stream (
    order_id VARCHAR,
    customer_id VARCHAR,
    amount DOUBLE,
    event_time BIGINT
) WITH (KAFKA_TOPIC='orders', VALUE_FORMAT='JSON', TIMESTAMP='event_time');

-- Continuously count orders per customer per 5-minute window
CREATE TABLE order_counts_5min AS
SELECT
    customer_id,
    COUNT(*) AS order_count,
    SUM(amount) AS total_amount,
    WINDOWSTART AS window_start,
    WINDOWEND AS window_end
FROM orders_stream
    WINDOW TUMBLING (SIZE 5 MINUTES)
GROUP BY customer_id
EMIT CHANGES;

-- Join order events with a customer enrichment table
CREATE STREAM enriched_orders AS
SELECT
    o.order_id,
    o.amount,
    c.customer_name,
    c.tier
FROM orders_stream o
LEFT JOIN customers_table c
ON o.customer_id = c.customer_id;

ksqlDB runs as its own server (separate from your Kafka brokers) and persists the results of CREATE TABLE AS SELECT ... back to Kafka topics, which are then queryable by downstream consumers or other ksqlDB queries.

10.1 Cluster sizing & capacity planning

A common question: "How many brokers do I need, and how many partitions should my topic have?"

Broker sizing (starting points):

  • A single modern broker (e.g., 16 vCPU, 32–64 GB RAM, 2–4 TB NVMe SSD, 10 Gbps NIC) can comfortably handle ~500 MB/s–1 GB/s of write throughput and tens of millions of messages per second if well-tuned — but production clusters almost always have 3+ brokers for replication and failure tolerance.
  • RAM is less about JVM heap (keep Kafka's JVM heap at 6–8 GB max — more causes GC problems) and more about the OS page cache. Kafka aggressively relies on the kernel to cache partition segments in memory. More RAM = more hot data served from memory without disk reads. A machine with 64 GB RAM and 6 GB JVM heap leaves ~55 GB as page cache.
  • NVMe SSDs are strongly preferred over HDD for mixed read/write workloads (replay, consumer groups at varying positions). Pure append workloads on spinning disk can work but are slower and more variable.

Partition sizing rules of thumb:

  • Target throughput method: if you expect 1 GB/s total write throughput for a topic, and one partition (with one consumer) can handle ~100 MB/s, you need at least 10 partitions. Add a safety buffer: 15–20.
  • Consumer parallelism method: if your processing job needs to run 30 consumer threads at peak, you need ≥30 partitions.
  • Don't pre-create 1000 partitions "just in case" — this strains the controller, replication, and leader election. Grow partitions incrementally (but remember, changing partition count breaks key-based ordering for existing keys in that topic).

10.2 Monitoring: the metrics that actually matter

Kafka exposes hundreds of JMX metrics. These are the ones that every data engineer should actually have on a dashboard:

Broker metrics (via JMX / Prometheus JMX Exporter):

  • kafka.server:type=BrokerTopicMetrics,name=MessagesInPerSec — message ingest rate
  • kafka.server:type=BrokerTopicMetrics,name=BytesInPerSec / BytesOutPerSec — throughput
  • kafka.controller:type=KafkaController,name=ActiveControllerCount — should be exactly 1; 0 = disaster
  • kafka.controller:type=KafkaController,name=OfflinePartitionsCount — should be 0 in a healthy cluster; any value > 0 means partitions with no available leader (data unavailability)
  • kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions — partitions where followers are behind. Should be 0; > 0 often means a broker is struggling or a disk is full.
  • kafka.network:type=RequestMetrics,name=TotalTimeMs (especially for FetchConsumer and Produce requests) — broker request latency

Consumer metrics (most critical for data pipelines):

  • Consumer Lag (records-lag-max, or via kafka-consumer-groups.sh --describe) — THE most important signal. It tells you the distance (in number of records) between the last committed consumer offset and the current end of the partition. Lag consistently growing = your pipeline can't keep up with the producer rate and will fall further behind over time.
  • records-consumed-rate — records per second your consumer is actually processing

Producer metrics:

  • record-error-rate — if this is non-zero, messages are being dropped/failed after all retries
  • request-latency-avg — end-to-end produce latency

Recommended tooling: Prometheus + Grafana with the JMX Exporter (for Kafka's JMX metrics) is the most common open-source stack. Confluent Control Center is the commercial option. Amazon MSK integrates with CloudWatch.

10.3 Security: encryption, authentication, authorization

Encryption in transit (TLS): configure Kafka listeners to use SSL or SASL_SSL protocol. All traffic between clients and brokers (and between brokers themselves for replication) is encrypted. This is a mandatory production requirement — Kafka, by default, sends everything in plaintext.

Authentication: Who is allowed to connect?

  • SASL/SCRAM: username+password authentication, stored in ZooKeeper/metadata. Easiest to set up for internal services.
  • SASL/GSSAPI (Kerberos): enterprise-standard, integrates with Active Directory / MIT Kerberos. Common in large financial institutions and enterprises.
  • mTLS (mutual TLS): the client presents a certificate that the broker validates. Strongest identity guarantee, no shared secrets. Kafka supports this natively with ssl.client.auth=required.
  • SASL/OAUTHBEARER: OAuth 2.0 / OIDC token-based auth. Modern choice for cloud-native environments, integrates well with identity providers (Okta, Keycloak, cloud IAM).

Authorization (ACLs): Who is allowed to do what?

Kafka has a built-in ACL system (kafka.security.authorizer.AclAuthorizer, or the newer StandardAuthorizer in KRaft mode). ACLs are defined on resources (Topic, Group, Cluster) with operations (Read, Write, Create, Delete, Describe, Alter).

bash
# Allow the "billing-service" principal to read from "orders" topic and use the "billing-service" consumer group
kafka-acls.sh --bootstrap-server localhost:9092 \
  --add --allow-principal User:billing-service \
  --operation Read --topic orders
kafka-acls.sh --bootstrap-server localhost:9092 \
  --add --allow-principal User:billing-service \
  --operation Read --group billing-service

In production, apply the principle of least privilege: the orders-producer service can only write to orders; it cannot read from it or write to any other topic. The billing-service consumer can only read from orders and use its own consumer group.

10.4 Multi-datacenter replication (MirrorMaker 2)

Running Kafka in a single datacenter creates a single point of failure for the entire event streaming backbone. Most production deployments at scale use multi-datacenter or multi-region replication.

MirrorMaker 2 (MM2) is the built-in solution (added in Kafka 2.4, a major improvement over the original MirrorMaker 1). MM2 is a Kafka Connect application that:

  • Continuously replicates topics from a source cluster to a destination cluster.
  • Remaps topic names to avoid collisions (e.g., orders on the us-east cluster becomes us-east.orders on the us-west cluster).
  • Translates offsets between the two clusters, so a consumer group that fails over to the secondary cluster can pick up near where it left off (not from the beginning).
  • Syncs consumer group offsets, ACLs, and topic configs.

Active-active (both clusters serving traffic) vs. active-passive (one cluster is primary, one is a standby) are the two common topologies. Netflix uses an active-active multi-region Kafka setup (see Part 11); this is also what Uber documents in their white paper.

10.5 Performance tuning checklist

Producer side:

  • [ ] Use compression.type=lz4 or zstd — typically 3–10x compression ratio for JSON/log data
  • [ ] Tune linger.ms (5–50ms) and batch.size (32–64KB) together for batching efficiency
  • [ ] Keep max.in.flight.requests.per.connection=5 when enable.idempotence=true
  • [ ] Use asynchronous sends with callbacks; don't get() (block) on every Future

Consumer side:

  • [ ] Set fetch.min.bytes / fetch.max.wait.ms to batch fetches and reduce round-trips
  • [ ] Increase max.poll.records for batch-friendly processing (500–2000 for high-throughput pipelines)
  • [ ] Make sure max.poll.interval.ms is greater than your actual max processing time for a batch
  • [ ] Use CooperativeStickyAssignor to reduce rebalance disruption
  • [ ] Process in parallel within a partition carefully (only if you can tolerate out-of-order processing within a partition, e.g., using thread pools with per-key sequencing)

Broker side:

  • [ ] Set num.io.threads and num.network.threads based on CPU count and workload
  • [ ] Pin separate disks for log storage (log.dirs): multiple disks spreads the I/O load
  • [ ] Tune log.segment.bytes (default 1 GB) and log.retention.hours/bytes for your retention strategy
  • [ ] JVM: use G1GC, -Xms6g -Xmx6g (heap should match exactly), -XX:MetaspaceSize=96m
  • [ ] OS: increase ulimit -n (open file descriptors) to at least 100,000 per broker process

10.6 Common pitfalls and anti-patterns

1. Too few partitions (the most common beginner mistake)

You create a topic with 1 or 3 partitions. It works fine in dev. In production, you discover that your consumer group can only run 3 consumers in parallel and you can't scale further without repartitioning (which is disruptive and breaks ordering for existing data). Solution: over-provision partitions slightly at topic creation time.

2. The consumer can't keep up (max.poll.interval.ms exceeded)

Your consumer fetches 500 records, sends them to an external API that's slow, and takes 8 minutes to process the batch. Kafka kicks the consumer out of the group (default max.poll.interval.ms = 5 minutes), triggers a rebalance, and the same records get reprocessed by a different consumer — infinite loop. Solution: reduce max.poll.records, increase max.poll.interval.ms, or move the slow work to a separate thread pool.

3. No DLQ / no error handling

One malformed message crashes the consumer, which restarts, crashes again, restarts... A bad message pins your consumer at that offset indefinitely while lag explodes on your other topics. Solution: always have a dead-letter-queue strategy (§6.5).

4. Using Kafka as a database / RPC substrate

Kafka is not designed for request/reply patterns. If service A needs a synchronous answer from service B, use gRPC or REST. If you're implementing "send a command and wait for a result" on top of Kafka, you're fighting the tool.

5. Ignoring schema governance until it's too late

Months after launch, you have 20 consumers reading a topic and the producing team wants to rename a field. Without a schema registry, this is a breaking change that requires coordinating every single consumer team simultaneously. With a schema registry and BACKWARD compatibility enforced, the producing team simply adds the new field with a default, consumers can upgrade asynchronously, and the old field is deprecated over time.

6. Growing consumer groups beyond partition count

Adding a 7th consumer instance to a consumer group reading a 6-partition topic: the 7th consumer sits completely idle, consuming resources but doing nothing. Scale consumer instances up to (not beyond) the partition count.

7. Committing offsets inside a database transaction but not atomically with Kafka

You write to Postgres and commit the Kafka offset — but in two separate steps. If you crash between the two, you either reprocess (double-write to Postgres) or lose the Kafka commit (lose data). Solution: use idempotent writes to Postgres (upsert by primary key using the Kafka record's unique identifier) so reprocessing is safe.

Part 11 — Real-World Case Study: Netflix Kafka at 2+ Trillion Events/Day

11.1 Scale and business context

Netflix is the most thoroughly documented Kafka deployment in the industry, making it the ideal case study. The numbers alone are staggering: Netflix processes over 2 trillion events per day across thousands of Kafka brokers. Every interaction a member has with the platform — a play, a pause, a search, a scroll, a rating, a title impression — must reach multiple downstream systems in near real-time.

Netflix operates in over 190 countries, with around 300 million subscribers as of 2025. Real-time data is not an optional feature for them: it actively drives personalization (which titles to show you), content strategy (which shows to commission), studio operations (encoding pipelines), advertising (ad-supported plan targeting), and service reliability (detecting and responding to streaming anomalies).

The breadth of the problem expanded dramatically in recent years. Netflix added ad-supported plans, live programming (NFL games, boxing events), and mobile games — all of which require analyzing member interactions across different business verticals simultaneously and in real time. This is what drove them to build a new class of real-time infrastructure.

11.3 Deep dive: the Real-Time Distributed Graph (RDG) pipeline

In October 2025, Netflix published the architecture of their Real-Time Distributed Graph (RDG) — a system that models member interactions across all of Netflix's product surfaces (video streaming, gaming, live events, ads) in real time.

The scale: 8 billion+ nodes, 150 billion+ edges, sustaining 2 million reads/second and 6 million writes/second. This graph powers personalization, ad targeting, and game discovery simultaneously.

Why a graph? And why real-time?

Netflix's older architecture used batch processing. A member's gaming behavior on Monday morning wouldn't influence their video recommendations until the next day's batch job ran. With live programming events (NFL games, boxing) and gaming, that latency is unacceptable — a member who just played a mobile game should immediately see more game recommendations, not 24 hours later.

Hard-won lessons from building the RDG:

Netflix's initial design had a single Flink job consuming all Kafka topics. This failed in production because different topics have radically different throughput patterns — a "member logged in" event fires once per session; a "streaming quality metric" event fires dozens of times per minute. Tuning a single job for all these patterns was impossible. They pivoted to one Flink job per Kafka topic, and one Kafka topic per node/edge type — more operational overhead, but each becomes independently tunable and scalable.

11.4 Keystone Pipeline and Data Mesh

Netflix's broader data routing layer is called Keystone, which processes up to 2 trillion messages per day, ingesting ~3 petabytes and outputting ~7 petabytes daily. It's the main fire hose: Keystone routes events to S3 (data lake), secondary Kafka clusters, Elasticsearch, and long-term analytical stores like Redshift and Hive.

On top of Keystone sits the Data Mesh platform, which wraps Flink's Table API behind standard SQL, letting teams outside the data infrastructure organization build pipelines without writing custom Java processors. Within the first year of its launch, 1,200 SQL processors had been created by teams outside the data infrastructure org — a textbook example of the "democratization" pattern: build complex infrastructure (Flink), then wrap it in a simple interface (SQL) so domain experts can self-serve.

11.5 Design lessons transferable to any team

Regardless of your scale (you are almost certainly not at Netflix's scale yet), these principles apply from day one:

1. Separate ingestion from consumption clusters early.

If you have many consumer groups reading at different rates, consider splitting your cluster topology before it becomes a performance problem. Netflix learned this lesson the hard way.

2. Treat durability configuration as a first-class engineering concern.

Netflix documented a case where data was permanently lost due to misconfigured acks, min.insync.replicas, and unclean.leader.election settings. These aren't defaults you set and forget — they are explicit SLA choices. Make them consciously and document them.

3. Don't stream all the things.

Netflix explicitly warns against migrating every pipeline from batch to real-time. When they did so indiscriminately, they documented the "pioneer tax": increased on-call burden, complex failure recovery, and JAR dependency hell. Batch remains the right choice when real-time doesn't add measurable business value. Stream what actually needs to be real-time.

4. One job / one topic = operational sanity at scale.

The monolithic "one Flink job for all topics" failed for Netflix. Isolation and independence matter — when each job is small and focused, it's easy to tune, redeploy, and attribute incidents.

5. Build on proven infrastructure rather than chasing novelty.

Netflix could have used a purpose-built graph database for the RDG. They chose Cassandra — a system they already operated at massive scale with deep internal expertise — and emulated graph semantics on top of it. The value of operational maturity and existing tooling often outweighs the theoretical elegance of the "right" specialized tool.

11.6 A second data point: Kafka at Uber

Uber offers a complementary case study to Netflix. As of Uber's published research, they manage one of the largest Kafka clusters in the industry, processing petabytes of data daily across tens of thousands of Kafka applications (drivers, riders, restaurants, couriers all generating events in real time).

Uber's key Kafka innovations:

Cluster federation: instead of one giant monolithic cluster, Uber operates many federated clusters, each with around 150 nodes. This makes scaling easier and reduces blast radius — a problem in one cluster doesn't affect the others. They built uReplicator (an improvement on MirrorMaker 1) to synchronize data across clusters and data centers.

Consumer proxy: the open-source Kafka consumer library embeds complex logic in the client, which made it extremely difficult for Uber to manage upgrades across tens of thousands of applications in four languages (Java, Python, Go, Node.js). They built a proxy layer that provides a thin, language-agnostic gRPC interface to applications and centralizes the Kafka consumer logic on the server side — upgrading the consumer library becomes a server-side deployment, not a massive client-side rollout.

Dead letter queues at scale: rather than retrying failed messages forever (blocking the queue) or dropping them (losing data), Uber built a standardized DLQ system across their Kafka infrastructure, with user-configurable retry limits and routing to dedicated error topics.

Tiered storage: Uber actively investigated (and implemented) tiered storage — keeping recent data on fast local SSDs for quick access, and offloading older data to cheaper remote storage (S3/GCS) transparently. This dramatically reduces the cost of long retention periods and allows the serving/storage layers to be scaled independently.

Kappa+ architecture: Uber's stream processing architecture (Flink + Kafka) supports backfill by running the same Flink SQL query against both the live Kafka topic (for real-time) and the archived Hive/HDFS dataset (for historical), without needing to maintain two separate jobs — a solution to the classic "how do I reprocess old data with my new stream processing logic" problem.
